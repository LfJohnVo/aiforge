# 2026-09-01 · Fase 5 · Upstream y canales

## Qué se hizo

**Ciclo de vida de tarea** (`upstream/tasks.py`): una sola implementación —`TaskState`,
`TaskRecord`, `TaskStore`, `TaskRunner`— con dos traducciones, la de MCP y la de A2A.
Construirlas por separado es como acaban las dos superficies discrepando sobre si una
tarea terminó. El estado autoritativo sigue viviendo en el checkpointer; este registro
sólo guarda lo que el checkpointer no puede: de qué hilo es cada `task_id` y el resultado
terminal, para que `get_status` pueda contestar cuando el grafo ya siguió adelante.

**Servidor MCP** (`upstream/mcp_server/`): las cinco tools de RF-03 —`ask`, `run_task`,
`get_status`, `search_knowledge`, `repo_graph_query`— montadas por streamable HTTP en el
mismo proceso y puerto que el resto de la API. La regla que la fase existe para sostener:
**un orquestador no hereda privilegios**. Si no propaga identidad de usuario final, el
techo es C0, y un techo declarado por encima del de la célula se recorta.

**A2A** (`upstream/a2a/`): Agent Card en las dos grafías de `/.well-known/`, JSON-RPC en
`POST /a2a` con `message/send`, `tasks/get` y `tasks/cancel`. La Card anuncia **skills, no
tools**: es pública para cualquier orquestador que alcance la célula, y enumerar el
catálogo interno diría qué sistemas corre el tenant.

**OpenAPI para Copilot Studio** (`upstream/openapi/`): el spec que genera FastAPI,
post-procesado —`$ref` en línea, `anyOf` de nulabilidad colapsados, objetos cerrados— y
recortado a tres endpoints. Post-procesado y no escrito a mano, porque un documento
escrito a mano se desincroniza del código con total seguridad.

**Canales**: WebSocket con autenticación en el handshake y eventos tipados; webhooks de
Teams y Slack con verificación de firma obligatoria; pipe opcional de OpenWebUI.

## Dos bugs reales, ambos de integración

### 1. El servidor MCP nunca arrancaba su gestor de sesiones

Starlette **no ejecuta el `lifespan` de una sub-aplicación montada**. El servidor MCP se
montaba correctamente, el log decía `mcp_server.built`, la ruta existía… y toda llamada
fallaba en caliente con `Task group is not initialized`. Un fallo en tiempo de petición,
no en el arranque: el despliegue habría parecido sano hasta la primera llamada de un
orquestador. Ahora el `lifespan` padre entra en el de la sub-app a través del
`AsyncExitStack`.

Este es el bug que justifica la forma del test: sólo aparece si un cliente real completa
el `initialize`. Cualquier prueba que llamase a las funciones de las tools directamente lo
habría aprobado.

### 2. Rechazo por cabecera `Host`

Resuelto el anterior, el cliente recibía `Invalid Host header`. El servidor MCP trae
protección contra *DNS rebinding* activada, y sin configurar sólo acepta loopback: detrás
de un proxy habría rechazado todo. La lista se deriva ahora de `AGENT_PUBLIC_URL`, con
`MCP_ALLOWED_HOSTS` para nombres adicionales. **La protección no se desactivó**, que era
la salida fácil; se configuró.

Queda una arista documentada: el endpoint canónico es `/mcp/` y `/mcp` responde 307. Todo
SDK de MCP sigue esa redirección —`create_mcp_http_client` fija `follow_redirects`
siempre—, así que no se fuerza; se anota.

## Un arreglo de deuda que la fase destapó

`Runtime` ganó dos campos obligatorios (`tasks`, `channel_settings`) y `tests/unit/test_api.py`
construía su propio `Runtime` a mano: dejó de compilar. En vez de parchear esa copia, la
construcción de una célula completa se movió a `tests/cell.py` y ahora la comparten los
tres módulos que la necesitan. Tres tests ensamblando la célula de tres maneras
ligeramente distintas es tener tres tests de una célula que nadie despliega.

Nota de método: los perfiles son modelos congelados, así que activar un canal en un test
se hace con `model_copy` reconstruyendo la sección, no asignando. Y `model_copy(update=)`
**no revalida**, de modo que sólo se sustituyen los campos conmutados y siempre por
modelos, nunca por diccionarios —pasar diccionarios produjo un `AttributeError` a diez
llamadas de distancia.

## Decisión registrada

[ADR-007](../adr/ADR-007-mcp-server-transport.md): el servidor MCP se publica sólo por
streamable HTTP. `ORCHESTRATORS.md` prometía en F0 también stdio; un servidor stdio es un
proceso hijo cuyo control de acceso es el permiso de ejecución, lo que rompe la invariante
de que toda superficie autentica al solicitante. El stdio se mantiene en el *cliente* MCP,
donde sí corresponde.
